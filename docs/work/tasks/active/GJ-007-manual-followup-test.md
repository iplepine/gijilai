## 목표

코드 자동화 전에, 상담 후 단발 후속 루프가 실제로 재방문과 결과 회수를 만드는지 수동(Wizard of Oz)으로 검증한다.

## 배경

사용자(개발자 본인 포함)가 상담을 받고 "해결됐거나 그럴싸하면" 다음날 앱을 안 연다. gijilai는 매일 쓰는 앱이 아니라 episodic 앱일 가능성이 크다. 매일 체크인 대신 `실천 → 며칠 뒤 1회 후속 → 성공 저금 또는 재상담`이 더 맞는지, 자동화에 투자하기 전에 사람이 직접 후속을 보내 가설을 검증한다. 상세 설계는 `docs/product/EPISODIC_FOLLOWUP_RETENTION.md`.

## 범위

포함:

- 최근 상담을 받은 유료 사용자 약 10명 선정
- 각자 상담의 실천 과제와 자연스러운 피드백 시점 파악
- 시점에 맞춰 후속 메시지 1회 수동 발송(가용 채널: 인앱/카카오/이메일 중 가능한 것)
- 후속 메시지 3분기 카피 준비: ① 해봤고 효과 있음 ② 안 됨/애매 ③ 아직 안 함
- 응답 회수 및 결과 분류 기록(됨/안 됨/안 함, 재상담 연결 여부)

제외:

- 자동 후속 트리거/스케줄 구현
- 매일 체크인 제거 코드 변경
- 가격/구독 구조 변경
- 상담 프롬프트 품질 튜닝

## 완료 기준

- [ ] 대상 사용자 약 10명 선정 및 각 실천 과제·후속 시점 정리
- [ ] 후속 메시지 3분기 카피 확정(추궁 아닌 돌봄 톤)
- [ ] 후속 1회 수동 발송 완료
- [ ] 응답을 됨/안 됨/안 함으로 분류해 기록
- [ ] 후속 응답률, "해봤다" 응답율, "안 됨"→재상담 연결 여부 집계
- [ ] 30/60일 재상담 복귀 관찰 시작점 기록
- [ ] 결과로 가설 채택/기각 판단(kill 기준 대비)

## 검증 계획

집계:

- 후속 응답률 = 응답자 수 / 후속 발송 수
- 실천 시도율 = "해봤다" 응답 수 / 응답 수
- 재상담 연결 = "안 됨/애매" 응답 중 재상담으로 이어진 수

판정:

- 응답·복귀가 의미 있으면 → R-003 다음 milestone(루프 자동화 범위 정의)로 진행
- kill 기준(후속 응답률 < 20% & 재상담 복귀 ≈ 0) 충족 시 → 자동화 중단, 상담 결과 품질 검증으로 방향 전환
