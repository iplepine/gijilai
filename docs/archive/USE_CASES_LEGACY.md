# 기질아이 유즈케이스 문서

현재 앱에 구현된 사용자 흐름을 기준으로 정리한 유즈케이스 문서다.
기획 희망안이 아니라 `app/`의 실제 라우트, `SPEC.md`, `docs/product/policies/` 문서를 기준으로 작성한다.

최종 동기화: 2026-05-01

## 1. 문서 목적

- 현재 서비스가 지원하는 핵심 사용자 여정을 한 번에 파악한다.
- 화면, 정책, 결제/권한 제약을 기능 단위로 연결해 본다.
- 이후 화면 추가/정책 변경 시 어떤 유즈케이스가 영향을 받는지 빠르게 판단한다.

## 2. 대상 사용자

### 2-1. 주요 사용자

- 3~7세 자녀를 둔 양육자
- 자녀의 기질을 이해하고, 기질 기반 양육 가이드를 받고 싶은 사용자
- 상담 후 실천과 기록까지 이어가고 싶은 사용자

### 2-2. 보조 사용자/행위자

- 공유 링크로 리포트를 열람하는 가족/배우자
- 구독 상태, 결제 상태, 분석 퍼널을 운영하는 운영자
- Flutter 앱 WebView 쉘을 통해 웹 기능을 사용하는 모바일 사용자

## 3. 서비스 한 줄 구조

기질아이는 다음 흐름을 중심으로 동작한다.

`랜딩/로그인 → 아이 등록 → 설문 → 리포트 확인 → AI 상담 → 실천 기록 → 상담 기록 회고 → 재상담/구독 전환/공유`

## 4. 핵심 유즈케이스 맵

| 구분 | 핵심 목적 | 대표 경로 |
|------|-----------|-----------|
| 유입/인증 | 서비스 소개 확인, 로그인 시작 | `/`, `/login` |
| 온보딩 | 아이 기본 정보 등록, 고민 수집 | `/settings/child/new`, `/intake` |
| 진단 | 아이/양육자 설문 완료 | `/survey/intro`, `/survey`, `/survey/child`, `/survey/parent`, `/survey/parenting-style` |
| 빠른 진단 | 아이 리포트를 먼저 보고 이후 전체 분석으로 확장 | `/survey?flow=quick`, `/report?child_only=true` |
| 해석 | 리포트 확인, 기질 해석 이해 | `/report` |
| 상담 | 현재 고민을 AI와 구조화 | `/consult` |
| 실천 | 상담 처방 기반 실천 수행 | `/practices` |
| 기록 | 상담 세션/실천 맥락 회고 | `/consultations`, `/consultations/[id]` |
| 관찰 | 실천/상담 장면을 따로 기록하고 다음 상담 맥락으로 남김 | `/observations` |
| 공유/추천 | 리포트 공유, 추천 코드 확산 | `/share`, `/shared/[id]` |
| 수익화 | 체험 종료 후 구독 전환/관리 | `/pricing`, `/pricing/complete`, `/settings/subscription` |
| 계정 관리 | 프로필, 아이, 알림, 로그아웃/탈퇴 관리 | `/settings/profile`, `/settings/notifications` |

## 5. 상세 유즈케이스

### UC-01. 서비스 가치를 확인하고 시작한다

- 목표: 사용자가 기질아이의 가치와 흐름을 이해하고 첫 진입 행동을 결정한다.
- 주요 사용자: 비로그인 사용자
- 진입 경로: `/`
- 선행 조건:
  - 웹 브라우저 비로그인 상태면 랜딩이 노출된다.
  - 앱 WebView 비로그인 상태는 랜딩 대신 로그인 진입으로 분기될 수 있다.
- 주요 흐름:
  1. 서비스 소개, 신뢰 요소, 핵심 CTA를 본다.
  2. 무료 검사/리포트 경험을 기대하고 다음 단계로 이동한다.
- 결과:
  - 로그인 또는 아이 등록/설문 플로우로 유입된다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 무료로 어디까지 가능한지, 시작 후 어떤 순서로 진행되는지
  - 시스템이 설명해야 하는 것: 기질아이의 핵심 가치가 `검사`가 아니라 `리포트 → 상담 → 실천` 흐름이라는 점
  - 선택 피로를 줄여야 하는 지점: 첫 화면에서 CTA를 여러 갈래로 늘리지 않고 `시작하기` 중심으로 모으는 것
  - 기본값/추천값: 비로그인 웹은 무료 검사 시작을 기본 추천값으로 둔다

### UC-02. 로그인하고 개인 세션을 연다

- 목표: 사용자가 개인 데이터와 리포트를 유지할 수 있는 세션을 만든다.
- 주요 사용자: 신규/기존 사용자
- 진입 경로: `/login`
- 선행 조건:
  - 로그인 제공 수단은 카카오, Apple, Google, 이메일이다.
  - 앱에서는 네이티브 로그인 오버레이와 딥링크/OAuth fallback을 지원한다.
- 주요 흐름:
  1. 사용자가 로그인 수단을 선택한다.
  2. 인증 성공 시 Supabase 세션이 연결된다.
  3. 이후 홈 또는 원래 진입하려던 화면으로 이동한다.
- 결과:
  - 개인별 아이, 설문, 리포트, 상담, 결제 데이터를 사용할 수 있다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 로그인하면 결과/기록이 기기 밖에서도 유지된다는 점
  - 시스템이 설명해야 하는 것: 소셜 로그인과 이메일 로그인의 차이보다 `내 기록을 이어서 보기 위한 로그인`이라는 목적
  - 선택 피로를 줄여야 하는 지점: 로그인 수단이 많아 보여도 화면 메시지는 한 가지 행동으로 느껴지게 만드는 것
  - 기본값/추천값: 앱에서는 네이티브 우선 로그인, 웹에서는 가장 전환이 높은 소셜 로그인을 상단 추천으로 둔다

### UC-03. 아이를 등록하고 분석 대상자를 만든다

- 목표: 분석과 상담의 기준이 되는 아이 프로필을 생성한다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/settings/child/new`
- 선행 조건:
  - 로그인 필요
- 주요 흐름:
  1. 아이 이름, 생년월일, 성별, 사진을 입력한다.
  2. 저장 후 홈에서 선택 가능한 아이 프로필이 생성된다.
  3. 다자녀인 경우 선택된 아이를 전역 상태로 유지한다.
- 결과:
  - 아이별 설문, 리포트, 상담, 실천 이력이 분리 관리된다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 아이 프로필 하나가 이후 모든 리포트와 상담의 기준이 된다는 점
  - 시스템이 설명해야 하는 것: 이름/생년월일/성별이 왜 필요한지와 수정 가능 여부
  - 선택 피로를 줄여야 하는 지점: 선택 아이를 전역으로 유지해 화면마다 다시 고르지 않게 하는 것
  - 기본값/추천값: 첫 등록 아이를 기본 선택 아이로 두고 이후 모든 흐름에 자동 연결한다

### UC-04. 접수 정보를 입력해 설문과 분석 맥락을 만든다

- 목표: 설문 문항과 솔루션 개인화에 필요한 기본 맥락을 수집한다.
- 주요 사용자: 설문을 시작하려는 사용자
- 진입 경로: `/intake`
- 선행 조건:
  - 개인정보 처리방침 동의와 면책 동의가 필요하다.
- 주요 흐름:
  1. 아이 이름/성별/생년월일을 입력한다.
  2. 양육 고민을 최대 3개 선택한다.
  3. 생년월일 기준으로 월령이 계산된다.
- 결과:
  - 이후 설문과 리포트, 상담 프롬프트에 연령/고민 맥락이 반영된다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 접수 정보는 단순 인적사항이 아니라 설문/리포트 개인화 입력이라는 점
  - 시스템이 설명해야 하는 것: 월령 계산과 고민 선택이 질문/가이드에 어떻게 반영되는지
  - 선택 피로를 줄여야 하는 지점: 고민 선택을 최대 3개로 제한하고 대표 카테고리만 먼저 보이게 하는 것
  - 기본값/추천값: 월령은 생년월일로 자동 계산하고, 고민 카테고리는 자주 선택되는 항목을 우선 배치한다

### UC-05. 아이와 양육자 설문을 완료한다

- 목표: 기질 리포트 생성을 위한 기초 데이터를 수집한다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/survey/intro`, `/survey`, `/survey/child`, `/survey/parent`, `/survey/parenting-style`
- 선행 조건:
  - 아이 등록 또는 로컬 intake 정보가 있어야 한다.
- 주요 흐름:
  1. 설문 안내 화면에서 `빠르게 아이 결과 먼저 보기` 또는 `처음부터 전체 분석 시작하기`를 선택한다.
  2. 아이 기질 설문을 진행한다.
  3. 빠른 경로는 child-only 리포트로 먼저 이동한다.
  4. 전체 경로는 이어서 양육자 기질, 양육 태도 설문까지 연속 진행한다.
  5. 응답은 진행률과 함께 저장되고 임시 복원이 가능하다.
- 결과:
  - 아이 진단, 양육자 분석, 기질 맞춤 양육 리포트 생성 재료가 확보된다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: `빠른 결과`와 `전체 분석`의 차이, 지금 선택이 어디까지 결과를 만드는지
  - 시스템이 설명해야 하는 것: 아이 설문만으로 먼저 볼 수 있는 영역과 양육자 설문이 추가되면 확장되는 영역
  - 선택 피로를 줄여야 하는 지점: 설문 시작 시 경로를 한 번만 고르게 하고, 도중에는 다음 문항에만 집중하게 만드는 것
  - 기본값/추천값: 첫 진입자는 `빠르게 아이 결과 먼저 보기`를 추천하되, 전체 분석 확장 CTA를 이후에 명확히 보여준다

### UC-06. 기질 리포트를 확인하고 해석한다

- 목표: 사용자가 아이/양육자/관계의 기질 특성을 이해한다.
- 주요 사용자: 설문 완료 사용자
- 진입 경로: `/report`
- 선행 조건:
  - 최소 아이 설문 데이터가 필요하다.
- 주요 흐름:
  1. 아이 진단 탭에서 기질 유형, 점수, 해석, 양육 가이드를 본다.
  2. 양육자 분석 탭에서 양육자 성향과 취약/강점 패턴을 본다.
  3. 기질 맞춤 양육 탭에서 부모-자녀 차이와 대처 원칙을 본다.
  4. 필요한 경우 리포트를 다시 생성하거나 공유 흐름으로 이동한다.
- 보조 플로우:
  - `child_only` 모드에서는 아이 진단 탭만 먼저 노출하고, 하단 CTA로 양육자 검사 또는 전체 리포트로 확장한다.
- 결과:
  - 사용자는 기질 기반 해석과 대화 스크립트를 얻는다.
- 비고:
  - 현재 정책상 리포트 자체는 무료 공개 영역이다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 점수 자체보다 `우리 아이가 왜 이렇게 보이는지`와 일상 해석이 핵심이라는 점
  - 시스템이 설명해야 하는 것: 각 탭이 무엇을 보여주는지, child-only 결과가 어디까지인지
  - 선택 피로를 줄여야 하는 지점: 한 화면에서 너무 많은 해석 옵션보다 현재 읽어야 할 탭과 다음 행동을 분명히 주는 것
  - 기본값/추천값: child-only 사용자는 아이 진단 탭을 기본으로 보고, 다음 추천 행동은 양육자 분석 확장 또는 상담 시작으로 제시한다

### UC-07. 홈에서 오늘 해야 할 다음 행동을 찾는다

- 목표: 기존 사용자가 현재 상태에 맞는 다음 행동을 빠르게 선택한다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/`
- 선행 조건:
  - 로그인 상태
- 주요 흐름:
  1. 선택된 아이의 프로필, 기질 배지, 양육자 배지를 본다.
  2. 미완료 검사, 오늘의 마법의 한마디, 오늘의 실천, 상담 CTA, 리포트 CTA 중 현재 상태에 맞는 카드를 본다.
  3. 체험 종료 임박 시 프리미엄 전환 카드를 본다.
- 결과:
  - 홈이 단순 대시보드가 아니라 상태 기반 액션 허브로 동작한다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 홈은 전체 요약이 아니라 `지금 해야 할 다음 행동`을 고르는 화면이라는 점
  - 시스템이 설명해야 하는 것: 왜 이 카드가 지금 보이는지, 체험/구독/실천 상태에 따라 무엇이 우선인지
  - 선택 피로를 줄여야 하는 지점: 동일 중요도의 카드 나열보다 현재 상태별 최우선 CTA를 1~2개만 강조하는 것
  - 기본값/추천값: 미완료 검사, 오늘의 실천, 상담 재개 중 가장 전환 가치가 큰 행동을 상단 추천으로 둔다

### UC-08. 현재 육아 고민을 AI 상담으로 풀어본다

- 목표: 사용자가 특정 문제 상황을 구조화해 기질 기반 해석과 처방을 받는다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/consult`
- 선행 조건:
  - 아이 등록 필요
  - 아이 기질 리포트 또는 설문 데이터 필요
  - 구독 또는 7일 체험 상태여야 상담 접근 가능
- 주요 흐름:
  1. 사용자가 자유 텍스트로 고민을 입력한다.
  2. 아이 나이/성별에 맞는 예시 칩과 모바일 음성 입력으로 입력을 보조받는다.
  3. AI가 공감 멘트와 기초 질문을 제시한다.
  4. 필요 시 follow-up 질문이 한 번 추가된다.
  5. 최종적으로 속마음 통역, 관계 해석, 오늘의 한마디, 실천 항목이 포함된 처방전을 받는다.
- 결과:
  - 사용자는 단순 조언이 아니라 현재 상황 중심의 맞춤 상담 결과를 받는다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 상담은 정답 생성기가 아니라 현재 상황을 구조화해 다음 행동을 정리하는 도구라는 점
  - 시스템이 설명해야 하는 것: 어떤 입력이 필요하고, 몇 단계 후 어떤 결과를 받게 되는지
  - 선택 피로를 줄여야 하는 지점: 자유 입력, 예시 칩, 음성 입력을 모두 주더라도 실제 선택은 `지금 말하기` 하나로 느껴지게 하는 것
  - 기본값/추천값: 나이/상황 기반 예시 고민 칩과 첫 질문 톤을 기본 추천으로 제공한다

### UC-09. 상담 결과에서 실천 항목을 선택하고 수행한다

- 목표: 상담 결과를 일상 행동으로 전환한다.
- 주요 사용자: 상담 완료 사용자
- 진입 경로: `/consult` 결과, `/practices`
- 선행 조건:
  - 기존 상담 세션과 ACTIVE 실천 항목 존재
- 주요 흐름:
  1. 상담 결과의 실천 항목이 저장된다.
  2. 실천 탭에서 세션별로 실천 항목이 그룹 표시된다.
  3. 사용자는 매일 했다/못했다와 한줄 메모를 남긴다.
  4. 기간 완료 후 회고를 남긴다.
- 결과:
  - 상담이 일회성 읽기로 끝나지 않고 실천 데이터가 누적된다.
- 비고:
  - 무료 사용자는 실천 이력을 제한적으로만 볼 수 있다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 상담 결과를 다 실천하는 것이 아니라 오늘 한 가지를 고르는 흐름이라는 점
  - 시스템이 설명해야 하는 것: 각 실천 항목이 언제, 얼마나, 어떻게 해보는 것인지
  - 선택 피로를 줄여야 하는 지점: 여러 실천을 한 번에 고르게 하지 않고 지금 시작할 1개를 정하게 만드는 것
  - 기본값/추천값: 상담 맥락상 가장 실행 난도가 낮고 효과가 빠른 실천 1개를 기본 추천으로 강조한다

### UC-10. 상담 기록을 세션 단위로 회고하고 이어간다

- 목표: 사용자가 과거 고민 흐름과 실천 맥락을 다시 확인한다.
- 주요 사용자: 상담 이력이 있는 사용자
- 진입 경로: `/consultations`, `/consultations/[id]`
- 선행 조건:
  - 저장된 상담 세션 또는 과거 상담 존재
- 주요 흐름:
  1. 기록 목록에서 진행 중/지난 상담 세션을 본다.
  2. 세션 상세에서 각 회차 상담, 처방전, 선택 실천을 타임라인으로 본다.
  3. 세션을 해결됨으로 전환하거나 추가 상담을 시작한다.
  4. 필요 시 개별 상담 또는 세션 전체를 삭제한다.
- 결과:
  - 사용자는 문제 해결 과정 전체를 시간축으로 회고할 수 있다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 개별 상담보다 세션 전체가 하나의 고민 해결 기록이라는 점
  - 시스템이 설명해야 하는 것: `진행 중`, `해결됨`, `지난 상담` 상태가 무엇을 뜻하는지
  - 선택 피로를 줄여야 하는 지점: 세션 목록에서 바로 다음 행동(추가 상담, 해결 처리, 회고 보기)을 분리해 주는 것
  - 기본값/추천값: 진행 중 세션을 기본 정렬 상단에 두고, 최근 실천과 연결된 세션을 우선 보여준다

### UC-11. 관찰 기록을 남겨 다음 상담 맥락을 축적한다

- 목표: 사용자가 실천/상담 장면을 따로 남기고 다음 상담의 맥락으로 축적한다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/observations`
- 선행 조건:
  - 로그인 상태
  - 아이 또는 상담 이력이 있으면 기록 연결성이 높아진다.
- 주요 흐름:
  1. 사용자가 아이별로 기록을 필터링한다.
  2. 상황, 내가 한 행동, 아이 반응, 메모를 입력해 관찰 기록을 남긴다.
  3. 최근 상담 또는 처방과 연결해 기록할 수 있다.
  4. 최근 상담의 액션 아이템에서 바로 기록 작성으로 이어질 수 있다.
  5. 저장된 기록을 다시 보고 삭제할 수 있다.
- 결과:
  - 최근 관찰 기록이 다음 AI 상담 질문/처방 생성의 컨텍스트로 활용된다.
- 비고:
  - 관찰 기록은 독립 기능처럼 보이지만 정책상 `상담 → 실천 → 기록` 루프의 일부다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 관찰 기록은 일기장이 아니라 다음 상담 정확도를 높이는 재료라는 점
  - 시스템이 설명해야 하는 것: 어떤 순간을 남기면 좋은지와 상담/실천과의 연결 방식
  - 선택 피로를 줄여야 하는 지점: 자유 메모를 길게 쓰게 하기보다 상황-내 행동-아이 반응 순서로 입력 틀을 주는 것
  - 기본값/추천값: 최근 상담 또는 최근 실천 항목을 기본 연결 대상으로 추천한다

### UC-12. 리포트를 가족과 공유하고 추천을 확산한다

- 목표: 사용자가 리포트를 가족과 공유하고 자연스럽게 추천을 유도한다.
- 주요 사용자: 리포트 보유 사용자, 공유 링크 수신자
- 진입 경로: `/share`, `/shared/[id]`
- 선행 조건:
  - 공유 가능한 리포트 존재
- 주요 흐름:
  1. 사용자가 카카오 공유, 링크 복사, 모바일 OS 공유를 선택한다.
  2. 공유 링크에는 추천 코드가 포함될 수 있다.
  3. 공유 링크 수신자는 공개 리포트 페이지에서 결과를 본다.
  4. 수신자가 로그인/설문으로 전환하면 앱 전역 추천 코드 적용 로직이 자동 실행될 수 있다.
- 결과:
  - 가족 공유와 추천 기반 유입, 쿠폰 발급 흐름이 발생한다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 공유는 결과 전달용인지, 가족 대화용인지, 추천용인지 목적이 다를 수 있다는 점
  - 시스템이 설명해야 하는 것: 공유받는 사람에게 무엇이 보이고 어디까지 공개되는지
  - 선택 피로를 줄여야 하는 지점: 카카오/링크복사/OS공유를 모두 주더라도 현재 기기에서 가장 자연스러운 공유 수단을 먼저 제안하는 것
  - 기본값/추천값: 모바일은 OS 공유 또는 카카오를, 데스크톱은 링크 복사를 기본 추천으로 둔다

### UC-13. 체험 종료 후 구독으로 전환한다

- 목표: 사용자가 상담/실천의 연속성을 위해 월 구독을 시작한다.
- 주요 사용자: 비구독 사용자
- 진입 경로: `/pricing`, `/pricing/complete`
- 선행 조건:
  - 로그인 상태
- 주요 흐름:
  1. 사용자가 가격과 함께 `리포트 → 상담 → 실천 기록 → 다음 상담` 지속관리 흐름을 확인한다.
  2. 웹이면 PortOne 정기결제, 앱이면 Apple/Google IAP로 분기된다.
  3. 첫 결제 또는 구독 재활성화를 완료한다.
  4. 성공 후 구독 관리 화면 또는 홈 흐름으로 돌아간다.
- 결과:
  - 상담, 실천 기록, 후속 상담 맥락이 하나의 지속관리 루프로 이어진다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 구독의 가치는 기능 해제보다 `다음 상담이 더 정확해지는 연속성`이라는 점
  - 시스템이 설명해야 하는 것: 앱에서 결제가 진행된다는 점, 체험 종료 후 무엇이 달라지는지
  - 선택 피로를 줄여야 하는 지점: 요금제/결제수단/플랜 옵션을 많이 고르게 하지 않고 월 구독 1안으로 정리하는 것
  - 기본값/추천값: 월 구독 단일안과 첫 달 혜택, 그리고 다음 행동으로 `앱 설치 후 구독 시작`을 기본 추천으로 제시한다

### UC-14. 구독 상태와 결제 이력을 관리한다

- 목표: 사용자가 현재 구독 상태를 이해하고 해지/재개를 수행한다.
- 주요 사용자: 구독 사용자
- 진입 경로: `/settings/subscription`
- 선행 조건:
  - 로그인 상태
- 주요 흐름:
  1. 현재 구독 상태, 결제수단 요약, 결제 이력을 확인한다.
  2. 웹 구독은 앱 내 해지/재개 API를 사용한다.
  3. 앱 IAP 구독은 각 스토어 관리 화면으로 이동해 관리한다.
- 결과:
  - 사용자가 해지 예약, 재개, 결제 수단 맥락을 직접 통제할 수 있다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 현재 구독이 활성, 해지 예약, 만료 중 어떤 상태인지
  - 시스템이 설명해야 하는 것: 웹 구독과 스토어 구독은 관리 위치가 다르다는 점
  - 선택 피로를 줄여야 하는 지점: 해지/재개/스토어 이동 같은 액션을 상태에 따라 하나씩만 강하게 보여주는 것
  - 기본값/추천값: 앱 IAP 구독은 해당 스토어 관리로 바로 보내고, PORTONE만 앱 내 해지/재개를 기본 동선으로 둔다

### UC-15. 내 정보와 알림 설정을 관리한다

- 목표: 사용자가 계정, 아이, 알림 선호, 탈퇴/로그아웃 상태를 유지 관리한다.
- 주요 사용자: 로그인 사용자
- 진입 경로: `/settings/profile`, `/settings/profile/edit`, `/settings/child/[id]`, `/settings/notifications`
- 선행 조건:
  - 로그인 상태
- 주요 흐름:
  1. 프로필 정보와 아이 목록을 본다.
  2. 프로필 사진/이름을 수정한다.
  3. 아이 정보를 수정하거나 삭제한다.
  4. 실천 리마인더 시간, 푸시 사용 여부, 마케팅 수신 동의를 관리한다.
  5. 필요 시 로그아웃하거나 회원 탈퇴를 진행한다.
- 결과:
  - 장기 사용에 필요한 프로필/알림 운영이 가능하다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 알림 설정은 마케팅보다 실천 리마인더와 재참여 루프를 위한 도구라는 점
  - 시스템이 설명해야 하는 것: 각 설정이 어디에 영향을 주는지와 언제든 변경 가능하다는 점
  - 선택 피로를 줄여야 하는 지점: 프로필, 아이, 알림, 탈퇴를 한 화면에서 섞지 않고 범주별로 나누는 것
  - 기본값/추천값: 실천 리마인더는 저녁 시간 기본값을 두고, 현재 사용 패턴에 맞는 추천 시간대를 제시한다

### UC-16. 법적 정보와 지원 채널을 확인한다

- 목표: 사용자가 서비스 이용 조건과 고객지원 경로를 확인한다.
- 주요 사용자: 전체 사용자
- 진입 경로: `/legal/terms`, `/legal/privacy`, `/legal/refund`, `/legal/support`, `/legal/about`
- 선행 조건:
  - 없음
- 주요 흐름:
  1. 약관, 개인정보 처리방침, 환불 정책을 읽는다.
  2. 문의가 필요하면 고객지원 메일로 이동한다.
- 결과:
  - 서비스 신뢰, 결제 판단, 문제 해결 경로를 확보한다.
- 의사결정 보강:
  - 사용자가 이해해야 하는 것: 법률 문서는 의무 고지이면서 동시에 결제/환불 판단 자료라는 점
  - 시스템이 설명해야 하는 것: 환불, 개인정보, 고객지원 채널을 어디서 확인할 수 있는지
  - 선택 피로를 줄여야 하는 지점: 약관/개인정보/환불/문의 경로를 섞지 않고 목적별로 분리하는 것
  - 기본값/추천값: 결제 직전에는 환불/지원 문서를 우선 연결하고, 일반 탐색에는 전체 법률 문서 허브를 기본 진입으로 둔다

## 7. 구현상 중요한 제약

- Flutter 앱은 WebView 쉘이며 핵심 도메인 로직은 Next.js 웹 앱이 담당한다.
- 하단 탭은 `홈 / 실천 / 상담 / 기록 / 내 정보` 5개로 고정된다.
- 내부 페이지 전환은 WebView 뒤로가기 이슈를 줄이기 위해 `router.replace()`를 기본으로 사용한다.
- 다자녀를 지원하지만, 많은 화면은 현재 선택된 아이 기준으로 필터링된다.
- 상담은 아이 기질 데이터가 있어야 의미 있게 동작하며, 양육자 기질 검사는 필수는 아니다.
- 관찰 기록은 별도 페이지가 있지만 정책상 독립 저널이 아니라 상담/실천 루프의 일부다.
- 리포트는 공개 영역이지만 상담/실천은 티어 영향이 있다.
- 현재 메인 수익화 플로우는 `/pricing` 기반 구독이며, `/payment`는 한국어 환경의 과거 결제/쿠폰 호환 흐름으로 남아 있다.
- 결제 수단 민감정보는 저장하지 않으며, 앱 구독은 스토어 상태 동기화에 의존한다.

## 8. 예외/보조 화면

아래는 메인 유즈케이스보다는 예외 처리 또는 개발용 성격이 강한 화면이다.

- `/auth/auth-code-error`: OAuth/인증 오류 안내
- `/payment`, `/payment/success`: 한국어 환경의 레거시 결제/쿠폰 및 검증 후처리 흐름
- `/pricing/complete`: 구독 결제 완료 콜백 처리
- `/test/llm-connection`: 개발용 LLM 연결 테스트

## 9. 문서 활용 권장 방식

- 화면을 추가할 때: 기존 UC에 속하는지, 새 UC가 필요한지 먼저 판단한다.
- 정책을 바꿀 때: `docs/product/policies/`와 함께 이 문서의 선행 조건/결과를 같이 갱신한다.
- QA를 할 때: UC별로 진입 조건, 성공 조건, 티어 제약을 체크리스트로 쪼개 사용한다.

## 10. 로드맵 연계 유즈케이스 후보

아래 항목은 [product-success-roadmap.md](plan/product-success-roadmap.md) 기준으로 추가 검토가 필요한 후보 유즈케이스다.
`## 5. 상세 유즈케이스`와 달리, 아직 구현 보강 또는 신규 정의가 필요한 흐름을 정리한다.

### UC-17. 리포트 해석의 신뢰 근거를 확인한다

- 목표: 사용자가 리포트 내용을 단순 결과가 아니라 설명 가능한 근거와 함께 이해한다.
- 주요 사용자: 리포트 열람 사용자, child-only 리포트 사용자
- 대표 경로: `/report`
- 연결 배경:
  - 무료 리포트가 다음 행동으로 이어지려면 `왜 이런 해석이 나왔는지`를 사용자가 납득해야 한다.
  - 기존 `UC-06`을 보강하는 성격이다.
- 기대 결과:
  - 리포트 열람 후 상담, 전체 분석, 공유로 이어지는 전환이 높아진다.

### UC-18. 상담이 우리 아이 상황에 맞는지 확인하고 시작한다

- 목표: 사용자가 상담 시작 전에 기대 결과, 적합성, 안전한 사용 범위를 확인한다.
- 주요 사용자: 첫 상담 진입 사용자, 결제 직전 사용자
- 대표 경로: `/consult`, `/pricing`
- 연결 배경:
  - 기존 `UC-08`은 상담 본문 흐름은 있으나, 시작 전 불안 해소와 신뢰 형성 단계는 약하다.
- 기대 결과:
  - 상담 시작 이탈이 줄고 체험/구독 이후 첫 상담 진입률이 높아진다.

### UC-19. 실천 후 변화를 바탕으로 후속 상담을 이어간다

- 목표: 사용자가 실천 후 생긴 변화, 실패, 추가 질문을 기반으로 다음 상담 회차를 자연스럽게 이어간다.
- 주요 사용자: 실천 중 사용자, 이전 상담 세션 보유 사용자
- 대표 경로: `/practices`, `/consultations/[id]`, `/consult`
- 연결 배경:
  - 기존 `UC-10`은 회고 중심이고, `다음 질문으로 이어지는 재상담 트리거`는 별도로 더 구체화할 필요가 있다.
- 기대 결과:
  - 상담이 단발성 처방이 아니라 연속 세션으로 인식된다.

### UC-20. 리마인더에서 한 번에 실천 또는 관찰 기록을 남긴다

- 목표: 사용자가 알림이나 홈 카드에서 최소 입력만으로 실천/관찰을 빠르게 기록한다.
- 주요 사용자: 실천 진행 중 사용자, 푸시/리마인더 허용 사용자
- 대표 경로: `/practices`, `/observations`, `/settings/notifications`
- 연결 배경:
  - 기존 `UC-11`, `UC-15`에는 기록과 알림이 있지만, 실제 입력 부담을 줄이는 흐름은 별도 정의가 필요하다.
- 기대 결과:
  - 기록 완료율이 높아지고, 다음 상담의 맥락 데이터가 더 안정적으로 쌓인다.

### UC-21. 공유받은 가족이 가입하거나 설문으로 전환한다

- 목표: 공유 링크 수신자가 단순 열람을 넘어서 로그인, 설문, 추천 코드 적용까지 이어진다.
- 주요 사용자: 공유 링크 수신자, 배우자/가족
- 대표 경로: `/shared/[id]`, `/login`, `/survey/intro`
- 연결 배경:
  - 기존 `UC-12`는 공유와 열람은 설명하지만, 수신자 전환 퍼널은 더 분리해서 관리할 가치가 있다.
- 기대 결과:
  - 공유가 단순 보기 기능을 넘어 신규 유입 채널로 작동한다.

### UC-22. 체험 시작부터 만료 직전까지 프리미엄 가치를 평가하고 구독을 결정한다

- 목표: 사용자가 체험 기간 동안 상담/실천 루프의 가치를 확인하고 만료 전에 구독 여부를 결정한다.
- 주요 사용자: 7일 체험 사용자, 비구독 기존 사용자
- 대표 경로: `/report`, `/consult`, `/pricing`, `/settings/subscription`
- 연결 배경:
  - 기존 `UC-13`은 구독 전환 자체를 다루지만, 체험 시작-사용-만료 직전 설득 흐름은 별도 관리가 필요하다.
- 기대 결과:
  - 체험 사용자의 구독 전환율과 만료 후 복귀율을 함께 개선한다.
